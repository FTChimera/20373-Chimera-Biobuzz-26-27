Control Hub Robot Controller Startup Failure
=============================================

Purpose
-------

This document records the evidence found in robotControllerLog.txt[1]4.txt,
the confirmed Robot Controller (RC) crash, the separate startup-compatibility
errors, and the recommended remediation paths.

This is not a robot-power or Control Hub firmware failure. The deployed RC app
is being terminated during its startup path. A terminated or repeatedly
restarting RC process can leave the Control Hub unavailable and appear to be
stuck with a blue status light.


Confirmed fatal crash
---------------------

The log contains one unhandled Android process crash:

  07-28 19:05:24.306 E AndroidRuntime: FATAL EXCEPTION: Thread-20
  java.util.ConcurrentModificationException
      at com.bylazar.configurables.Plugin.onRegister(ConfigurablesPlugin.kt:255)
      at com.bylazar.panels.plugins.Plugin.registerInternal$Panels_release(Plugin.kt:84)
      at com.bylazar.panels.plugins.PluginsManager.init(PluginsManager.kt:142)
      at com.bylazar.panels.Panels.initPanels$Panels_release(Panels.kt:96)
      at com.bylazar.panels.Panels$StartRoutine.run(Panels.kt:109)

This is an uncaught exception in the FullPanels library, not an exception from
TeamCode's Field utility, autonomous paths, hardware map, or a selected OpMode.

Android responds by terminating the entire process:

  Process: com.qualcomm.ftcrobotcontroller, PID: 972
  RCActivity: onPause()
  Robot Status: stopped, internal error
  FtcRobotControllerWatchdogService: onDestroy()

The RC app then begins another launch under a new process ID. If the same
startup race occurs again, the RC cannot remain ready long enough to serve the
Driver Station.


Why FullPanels runs twice
-------------------------

build.dependencies.gradle declares:

  implementation 'com.bylazar:fullpanels:1.0.12'

That external Gradle dependency pulls in:

  com.bylazar:panels:1.0.5
  com.bylazar:configurables:1.0.5
  com.bylazar:limelightproxy:1.0.4
  and other FullPanels modules.

"External" means that the code is downloaded by Gradle as an Android archive
(AAR); its source is not stored in this repository. Therefore TeamCode cannot
change its behavior by editing an OpMode or Field.java.

The Panels AAR registers its own FTC @OnCreateEventLoop hook:

  com.bylazar.panels.Panels.attachEventLoop(...)

Its compiled implementation starts a fresh Java Thread containing
Panels$StartRoutine every time the FTC SDK creates an event loop. It has no
AtomicBoolean, synchronized block, or other once-only guard.

The log proves that the hook was invoked twice for PID 972:

  07-28 19:05:20.580 ... Panels.attachEventLoop(...)
  07-28 19:05:20.598 ... Panels.attachEventLoop(...)

Those calls start two concurrent Panels initialization threads. Both register
the Configurables plugin and iterate its mutable ArrayList. The log shows both
threads discovering the same fields immediately before the fatal crash:

  Thread 1241: PANELS: Field startingPose ... is null
  Thread 1240: PANELS: Field startingPose ... is null
  Thread 1241: ConcurrentModificationException

The library's unguarded duplicate initialization is the direct cause of the
fatal crash.


What is not the cause
---------------------

Field.java is not responsible for this startup failure.

FTC SDK 11.2.1 discovers classes using Class.forName(name, false, loader).
The false parameter loads a class without running its static initialization.
Also, no compiled TeamCode source references Field outside Field.java itself.

Field.Shapes and Field.Boundaries do create JTS geometries when an enum value is
actually used. That is not happening during ordinary FTC class discovery. Their
geometry constructors do not read Constants.currentBot; robot dimensions are
only read later when contact-state methods run.

The fatal stack trace contains only FullPanels / Android code. It does not
contain Field, JTS, Pedro, Constants, an OpMode, or robot hardware code.


Separate Sloth and dependency compatibility problem
---------------------------------------------------

The project also applies Sloth/Sinister:

  TeamCode/build.gradle
    classpath "dev.frozenmilk:Load:0.2.4"
    apply plugin: 'dev.frozenmilk.sinister.sloth.load'
    implementation("dev.frozenmilk.sinister:Sloth:0.2.4")

TeamCode currently has no source usage of a dev.frozenmilk API. However, Sloth
installs an FTC @OnCreate hook and performs a full APK class scan at RC startup.
It also preloads EasyOpenCV, creates custom class loaders, uses a watcher under
/sdcard/FIRST/dairy/sloth, and reflects into private FTC SDK internals.

Sloth's scanner uses reflection that resolves every scanned class's method
types. FullPanels pulls in a JVM-only Okio artifact through this path:

  fullpanels:1.0.12
    -> limelightproxy:1.0.4
      -> okhttp:4.10.0
        -> okio-jvm:3.0.0

Okio's JVM classes use APIs absent from the Control Hub's Android runtime,
including:

  java.nio.file.Path
  java.nio.file.attribute.FileTime
  java.time.Duration
  java.time.Instant
  java.lang.ClassValue
  sun.misc.Signal

The log contains 828 Sloth/Sinister scanner failures. Examples include:

  NoClassDefFoundError: java.nio.file.Path
  Scanning Class: class okio.Okio__JvmOkioKt

  NoClassDefFoundError: java.time.Duration
  Scanning Class: class kotlinx.coroutines.time.TimeKt

These errors are caught by Sloth, so they are not the particular fatal
ConcurrentModificationException above. They still impose substantial startup
work, produce thousands of log lines, and make the RC less reliable.

Sloth also preserves dynamic load state at:

  /sdcard/FIRST/dairy/sloth/loaded.jar

That file can survive an RC app reinstall. Remove it from an affected Control
Hub while diagnosing this issue so stale dynamically-loaded code cannot remain
involved.


Why moving the Maven repository does not fix this
-------------------------------------------------

The ByLazar Maven repository can be declared either in the TeamCode dependency
script or in the root build.gradle allprojects repositories block. The latter
is a valid installation layout and makes the repository visible to every Gradle
subproject.

Repository placement controls where Gradle downloads an artifact. It does not
change the artifact version or the code inside it.

After the repository move, Gradle still resolves exactly:

  com.bylazar:fullpanels:1.0.12
  -> com.bylazar:panels:1.0.5

Therefore the same unguarded Panels.attachEventLoop implementation remains in
the APK and the fatal crash remains possible.


Recommended solutions
---------------------

1. Remove FullPanels for the most reliable immediate fix.

   Remove com.bylazar:fullpanels:1.0.12, then remove or replace TeamCode's
   FullPanels imports, @Configurable annotations, PanelsTelemetry calls, and
   Panels field-drawing calls. This removes the fatal startup hook, the
   Configurables plugin, Limelight proxy, and JVM-only Okio transitive
   dependency.

   Do not expect the "Enable/Disable Panels" OpMode to be a reliable recovery
   mechanism: Panels has already started its background initialization before
   that OpMode can be selected.

2. Fork and patch the Panels module if FullPanels must remain.

   Fork the FullPanels source repository and modify the module that defines
   com.bylazar.panels.Panels. Preserve the com.bylazar.panels package name so
   existing imports keep working.

   Panels.attachEventLoop must always rebind the OpMode listener to the newly
   created FTC event loop, but must initialize Panels only once per RC process.
   The library-side Kotlin logic should have this shape:

     private val startupScheduled = AtomicBoolean(false)

     @JvmStatic
     @OnCreateEventLoop
     fun attachEventLoop(context: Context, eventLoop: FtcEventLoop) {
         val manager = eventLoop.opModeManager
         manager.unregisterListener(INSTANCE)
         manager.registerListener(INSTANCE)

         if (!startupScheduled.compareAndSet(false, true)) {
             return
         }

         Thread(
             StartRoutine(context.applicationContext, eventLoop),
             "Panels-StartRoutine"
         ).start()
     }

   AtomicBoolean is essential. A normal Boolean check is not safe because the
   two observed calls were only 18 milliseconds apart.

   Publish the patched module under a team-owned Maven coordinate, then exclude
   the original transitive panels module and use the patched one:

     implementation('com.bylazar:fullpanels:1.0.12') {
         exclude group: 'com.bylazar', module: 'panels'
     }
     implementation 'your-team-group:panels:1.0.5-chimera.1'

   A local Gradle module can be used during development instead of publishing,
   but the original com.bylazar:panels module must still be excluded to avoid
   duplicate classes.

   This patch fixes the fatal race only. It does not remove the incompatible
   limelightproxy -> okhttp -> okio-jvm dependency.

3. Remove Sloth/Sinister as a separate hardening change.

   Remove these three entries from TeamCode/build.gradle:

     classpath "dev.frozenmilk:Load:0.2.4"
     apply plugin: 'dev.frozenmilk.sinister.sloth.load'
     implementation("dev.frozenmilk.sinister:Sloth:0.2.4")

   This will stop Sloth's startup class scans, unsupported-class errors, custom
   class loading, native EasyOpenCV preloading, and persistent loaded.jar
   behavior. It does not by itself guarantee that FullPanels will not start
   twice, because Panels has its own FTC lifecycle hooks.

4. If retaining FullPanels, eliminate the JVM-only network stack.

   The patched dependency graph must not package okio-jvm:3.0.0 on a Control
   Hub. Exclude or replace the FullPanels limelightproxy module with an Android
   compatible implementation. Do this only after checking whether any needed
   Panels feature relies on that module.

5. Upgrade only to an explicitly tested FullPanels release.

   A newer vendor release may fix the thread-safety defect, but do not assume
   that moving repositories selects a newer version. Pin a specific version,
   inspect its resolved dependency graph, and test startup on the actual
   Control Hub Android version before adopting it.


Suggested diagnostic sequence
-----------------------------

1. Recover a Control Hub using the normal REV / FTC procedure.
2. Delete /sdcard/FIRST/dairy/sloth/loaded.jar if present.
3. Deploy an APK with both FullPanels and Sloth removed. It should reach the RC
   ready state without FullPanels, Sinister, or AndroidRuntime fatal entries.
4. If Panels is necessary, test the patched once-only Panels module without
   Sloth. Verify that exactly one Panels$StartRoutine starts per RC process.
5. Verify the post-boot robotControllerLog.txt before adding additional
   libraries. There must be no AndroidRuntime FATAL EXCEPTION and no recurring
   Sinister NoClassDefFoundError entries.


Related changes that do not solve this crash
--------------------------------------------

Moving the ByLazar Maven repository to root build.gradle is appropriate Gradle
configuration but is runtime-neutral.

The current worktree also adds:

  implementation 'org.psilynx.psikit:core:0.2.0'
  implementation 'org.psilynx.psikit:ftc:0.2.0'

These do not fix FullPanels. PsiKit core resolves as a standard JVM artifact
while it is used only by src/test simulation code. It should not be packaged
in the RC application as an implementation dependency; use testImplementation
for the simulator-only core dependency, and do not include the FTC artifact
unless production Android code needs it.


Bottom line
-----------

The first blocking defect is the FullPanels 1.0.5 Panels startup race:

  two event-loop hooks
    -> two Panels$StartRoutine threads
      -> concurrent Configurables registration
        -> ConcurrentModificationException
          -> Robot Controller process termination

Remove FullPanels or fork and patch its event-loop initialization with an
AtomicBoolean guard. Then remove Sloth and the JVM-only Okio path to prevent
the separate startup compatibility failures.
