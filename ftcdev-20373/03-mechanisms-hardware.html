03 / Subsystems

Put robot behavior behind a mechanism.

A profile-managed mechanism gets a HardwareMap and active RobotConstants, resolves its own parameters, participates in aggregate updates, and becomes available only after its profile registers it. This prevents each op mode from inventing a new hardware construction path.

Call a mechanism from an OpMode

Once a mechanism is registered, callers should request it through the aggregate and invoke its public behavior. For example, an explicit intake action can be used in a focused test while normal teleop lets periodic(...) consume its configured trigger bindings.

Robot robot = Constants.createRobot(hardwareMap, RobotMode.TELEOP);
RobotDrive drive = robot.requireDrive();
Intake intake = robot.get(Intake.class);

waitForStart();
if (intake != null) intake.HalfPower();
sleep(250);
if (intake != null) intake.Stop();

// Shared teleop normally delegates all configured controls here:
robot.periodic(new State(driverBindings, RobotMode.TELEOP));

The Mechanism contract is small on purpose

public abstract class Mechanism {
    protected HardwareMap hardwareMap;
    protected RobotConstants bot;

    protected <P extends Params<P>> P resolveParams(
            Class<? extends Mechanism> mechanismClass, P defaultParams) {
        return bot.getMechanismParams(mechanismClass, defaultParams)
                .updateFromBot(bot);
    }

    public abstract void periodic(State state, RobotMode mode);
}

The small API is the point. A mechanism owns its hardware and per-loop behavior; the op mode owns the loop. Implement periodic(...) even when it intentionally does nothing, because the aggregate container calls a consistent surface. Autonomous mechanisms must not consume teleop bindings.

Existing examplesmechanisms/RobotDrive.java resolves stick bindings and delegates to MecanumDrive. mechanisms/Intake.java resolves power/binding parameters, creates a Motor, and combines trigger command values in periodic(...).

Use the aggregate container for shared op modes

Robot constructs every class in bot.Mechanisms, keeps typed lookup methods, and fans a mode-aware State update to every mechanism. It is the normal shared-teleop construction path.

Robot robot = Constants.createRobot(hardwareMap, RobotMode.TELEOP);
RobotDrive drive = robot.requireDrive();
Intake intake = robot.get(Intake.class);

// One updated input view; one aggregate periodic call each loop.
driver.update();
robot.periodic(new State(driverResult, RobotMode.TELEOP));
MethodUse it when
get(SomeClass.class)The mechanism is optional across profiles. Handle null intentionally.
require(SomeClass.class)The op mode cannot run safely without it. A missing registration should fail clearly.
has(SomeClass.class)A test or conditional path needs to inspect the aggregate before choosing work.
all()Telemetry or generic inspection needs the registered set.

Workflow: add a profile-managed mechanism

  1. Create the class under mechanisms/ or an appropriate library/hardware/... package, extending Mechanism.
  2. Add a nested params type implementing Mechanism.Params<T>. Give it copy(), updateFromBot(...), and focused builder methods for meaningful local values.
  3. Use resolveParams(NewMechanism.class, new PARAMS()) in the constructor before touching hardware.
  4. Construct lower-level wrappers such as Motor inside the mechanism, not in every caller.
  5. Implement periodic(State, RobotMode). Keep it safe when bindings are absent and suppress teleop input in autonomous mode.
  6. Register the class with .addMechanism(NewMechanism.class, params) in every supporting profile.
  7. Add a narrow Constants.createNewMechanism(...) helper only when direct callers need it; otherwise prefer the aggregate.
Do not skip registrationMatching the constructor signature alone is not enough. RobotConstants.createMechanism(...) intentionally rejects an unregistered class.

Do not confuse mechanisms with direct SDK devices

The repo also has custom device classes under library/hardware/hardwareDevice/. These represent an FTC SDK registration/use path and are appropriate for direct hardwareMap.get(...) in a lower-level test or device flow. They are not automatically part of the profile mechanism set.

Profile-managed

RobotDrive, Intake, Vision (which owns Limelight), and wrapper-side RGB indicator use the Mechanism factory path.

Direct devices

SlidesMotor, RevPotentiometer, and the device-level RGBIndicator are SDK-facing classes used through hardware mapping and dedicated tests.

Validate mechanism construction in layers

A safe validation ladder
  1. Build :TeamCode:assembleDebug after changing constructors, params, or registrations.
  2. For pure parameter behavior, add or update a JVM test.
  3. Use a matching tests/ftcSdk/*FactoryTest style flow to validate profile creation on hardware.
  4. Only then drive the mechanism from a shared or match op mode.
