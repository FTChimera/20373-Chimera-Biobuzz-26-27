03 / Subsystems

Mechanisms all share one loop contract: periodic(State) plus stop().

The base class takes HardwareMap and RobotConstants in the constructor, resolves copied params through the active profile, and leaves mode and match context inside State rather than in an extra method argument.

What this chapter covers

Use this page before changing code in the matching source areas.

  • Mechanism exposes public abstract void periodic(State robotState) and public abstract void stop().
  • Robot is itself a mechanism that aggregates the configured mechanism instances in class-name order.
  • Robot.periodic(State) updates the helper, injects robot and alliance data into state, then dispatches mechanism work.
  • Robot.stop(boolean) can stop mechanisms without immediately saving Blackboard handoff values.
  • Intake, RobotDrive, and Vision are the current profile-managed subsystems available in the active robot profile.
  • Direct device wrappers such as SlidesMotor, RevPotentiometer, and RGBIndicator live outside the aggregate mechanism set.

Base contract snapshot

This is the exact abstract surface every profile-managed mechanism must satisfy.

public abstract class Mechanism {
    public abstract void stop();
    public abstract void periodic(State robotState);
}

What Robot adds on top of Mechanism

The aggregate robot is more than a bag of getters.

  • It reads alliance color from Blackboard during construction and stores the chosen RobotMode beside that alliance.
  • It runs Common.init(color) once so alliance-aware planner pose containers point at the selected side.
  • It builds each configured mechanism with bot.createMechanism(map, mechanismClass).
  • It exposes convenience accessors like requireDrive(), requireIntake(), and requireVision().
  • It owns helper-backed voltage and op mode timing, so mechanisms can read them through State when needed.

Lifecycle details worth documenting

These behaviors are easy to miss if you only read op modes.

  • Robot.start() starts the helper and calls startVision(Vision.Pipeline.APRIL_TAG).
  • Robot.periodic(State) throws when the supplied state mode does not match the robot’s configured mode.
  • lastState is recorded during periodic and later used by saveEndVals().
  • stop() defaults to stop(true), but autonomous code can call stop(false) to delay pose persistence until velocity settles.
  • Teleop shutdown clears Blackboard items except driver preference, while autonomous shutdown writes pose and alliance when possible.

Hardware ownership boundary

If code needs to coordinate motors, follower state, intake behavior, or camera results over time, it belongs in a mechanism or in Robot. If it only wraps one SDK device type, it usually belongs under library/hardware and can be tested directly.

That split matters for documentation too: describe aggregate behavior in the mechanism chapters, and describe one-device constructors or sensors in hardware-specific notes or test instructions instead of pretending they are full subsystems.

Safe extension rules

New mechanism code should match the current architecture rather than invent a parallel one.

  • Resolve profile params through resolveParams(...) instead of reading raw robot constants everywhere.
  • Use State for mode, bindings, alliance, helper, and robot access instead of passing extra globals around.
  • Let Robot own startup and shutdown sequencing so Blackboard persistence stays centralized.
  • Add Driver Station tests under tests/ or tests/ftcSdk/ when a behavior touches real hardware.

One aggregate owner

Keep only one live instance of each profile-managed mechanism in a match flow. The source is built around the aggregate robot being that owner, so duplicate mechanism construction in op modes would bypass the shared lifecycle and handoff rules documented here.
