06 / Autonomous

Use one follower and one scheduler execution loop.

Pedro pathing and Ivy scheduling are separate concepts that meet in an FTC lifecycle class. The repository creates followers from the active robot profile, uses PathChain as the reusable path container, composes commands with Ivy, and deliberately keeps scheduler execution and follower updates visible.

Call the shared autonomous base from a variant

For a simple shared Ivy autonomous, the new class supplies the path provider and passes it to IvyAuton. The inherited base owns hardware construction, scheduler setup, command execution, follower updates, and Blackboard pose handoff.

@Autonomous(name = "My Red Auto")
public class MyRedAuto extends IvyAuton {
    static class Paths extends IvyAuton_Paths {
        private final Pose start = new Pose(36, 12, Math.toRadians(180));
        @Override protected Pose getStartingPose() { return start.copy(); }
        @Override protected PathChain getPath1() {
            Path path = new Path(new BezierLine(start, new Pose(36, 36)));
            path.setHeadingInterpolation(
                HeadingInterpolator.linear(start.getHeading(), Math.toRadians(180)));
            return new PathChain(path);
        }
    }
    public MyRedAuto() { super(AllianceColor.RED, new Paths()); }
}

Start from the active profile follower

Use Constants.createFollower(hardwareMap). It delegates to the selected RobotConstants.createFollower(...), where FollowerBuilder receives profile drive names/directions, path constraints, and Pinpoint localizer constants. Do not create a second standalone FollowerBuilder inside an autonomous op mode.

follower = Constants.createFollower(hardwareMap);
follower.setStartingPose(startPose);
Configuration boundaryFollower tuning and Pinpoint geometry belong in library/robot/RobotConfigurations.java and RobotConstants.java. Autonomous geometry belongs near the autonomous path provider or planner step.

Build PathChain objects with explicit heading behavior

Use a PathChain even when the geometry contains only one Path. Place heading interpolation next to the geometry rather than relying on external defaults.

Path path = new Path(new BezierLine(STARTING_POSE, endPose));
path.setHeadingInterpolation(HeadingInterpolator.linear(
    STARTING_POSE.getHeading(), endPose.getHeading()));
return new PathChain(path);

Use BezierLine for a direct segment and BezierCurve when control points express the route better. EquationCurve is a Pedro-specific adapter for an equation-through-endpoints model; use it only when that model really fits the path.

Ivy owns command composition, not the FTC loop

Ivy commands are assembled with existing operations such as Commands.instant(...), Commands.waitMs(...), Groups.sequential(...), and PedroCommands.follow(...). For an aggregate robot, use RobotIvyBuilder so commands retain the selected mode and mechanism checks. The FTC op mode still calls Scheduler.execute() once per loop. A command sequence does not run by itself.

RobotIvyBuilder commands = robot.build();
Scheduler.schedule(Groups.sequential(
    commands.runIntakeHalfPower(),
    commands.followPath(paths.getPath1(), true),
    commands.startIntake(),
    waitMs(1000),
    commands.stopIntake(),
    Commands.instant(this::requestOpModeStop)
));
Avoid duplicate ownershipDo not schedule two infinite updates for the same mechanism. Do not add a second follower.update() loop if the selected shared base already updates the follower in loop().

The shared iterative IvyAuton pattern

opModes/IvyAuton.java is an abstract iterative base. A concrete variant supplies an AllianceColor and an IvyAuton_Paths implementation. The base initializes an autonomous aggregate plus RobotIvyBuilder, schedules its mode-aware periodic and representative command sequence, executes Ivy in the iterative loop, and lets Robot.stop() store pose/alliance handoff in Blackboard.

Use this for

Shared match-style autonomous behavior that benefits from a common lifecycle and variant-specific geometry.

Do not use this for

A raw quick test, a blocking SDK experiment, or a second scheduler abstraction. Put those in tests/ or learn from the unannotated examples.

Workflow: make a new autonomous safely

  1. Choose shared IvyAuton, a planner test, or a fresh LinearOpMode based on whether the behavior is shared match code, planner experimentation, or a focused test.
  2. Define and validate the start pose. Set it on the follower before running any paths.
  3. Build each PathChain with explicit heading interpolation.
  4. Decide which owner calls follower.update(); preserve exactly one active update path.
  5. Schedule commands only after Scheduler.reset().
  6. Use stop() to persist pose when the next teleop will use Blackboard handoff.
  7. Validate individual geometry in a safe test before combining mechanisms and timing.
