07 / Planning

Use the current planner chain deliberately and treat vision-generated intake paths as explicit, filtered helpers.

PlanBuilder wraps a PathPlannerList. Common and AlliancePoses provide alliance-aware pose containers. Vision manages Limelight results, while IntakeBallPath turns detector output into a forward Pedro route when enough verified data is supplied.

What this chapter covers

Use this page before changing code in the matching source areas.

  • PlanBuilder.startGardenPose(robot) is the active entry point used by Garden8.
  • Common.init(alliance) only sets alliance selection on pose containers; many stored pose values are still zero poses.
  • AlliancePoses.pose() returns the red or blue copy based on the last selected alliance color.
  • Vision.periodic(State) updates orientation and camera results every cycle and can trigger an auto-intake follow request in teleop.
  • IntakeBallPath.generateIntakePathFromCam(...) is the fully featured overload; the no-argument overload currently returns an empty PathChain.
  • The strongest current detector path logic filters weak detections, de-duplicates close targets, scores forward sequences, and smooths the resulting path.

Planner chain snapshot

This reflects the public PlanBuilder methods used by the current autonomous flow.

PathPlannerList list = PlanBuilder.startGardenPose(robot)
        .shootPreloads()
        .intakeGarden()
        .build();

PlanBuilder state machine facts

The fluent API is stateful and enforces position transitions.

  • startGardenPose seeds the list with FromStartGardenPose.
  • shootPreloads() changes the tracked position from GARDEN_START to GARDEN_SHOOT.
  • intakeGarden() is only legal after the shoot step and throws for other positions.
  • followPath, linearPathTo, and waitMs are utility additions layered on the same planner list.
  • schedule() delegates to the built PathPlannerList.

Common and AlliancePoses boundaries

These helpers are structural, not finished match geometry.

  • Common.StartPoses, IntakePoses, and ShootPoses each store mirrored AlliancePoses fields.
  • The current constructor values for those containers are mostly new Pose() placeholders.
  • Common.init(color) chooses alliance on the stored containers but does not measure or populate field coordinates.
  • AlliancePoses.Red() and Blue() return copies, which helps callers avoid mutating the shared containers.

What the full IntakeBallPath overload actually does

The source-backed detection pipeline is more selective than a naive nearest-target pick.

  • It rejects missing detector lists and non-positive requested counts immediately.
  • It scores detections with a confidence and target-area weighted first pass before building candidates.
  • It rejects low-confidence, tiny-area, too-near, too-far, or too-far-lateral detections.
  • It converts robot-relative readings into field poses through MathUtils.offsetPoseInRobotFrame(...).
  • It de-duplicates candidates within a merge distance, then chooses the best increasing-forward sequence.
  • It builds either a Pedro curve-through chain or an adaptive-handle Bezier chain based on turn angle and waypoint spacing.

Vision integration reality check

The teleop auto-intake button path in Vision.periodic(State) currently calls the no-argument generateIntakePathFromCam() overload, which returns an empty PathChain. The richer overload exists in the library, but the teleop trigger path is still only scaffolded.

That means the docs should distinguish between the implemented path-generation library and the currently lightweight teleop trigger integration, rather than claiming end-to-end autonomous intake by camera is already finished.
