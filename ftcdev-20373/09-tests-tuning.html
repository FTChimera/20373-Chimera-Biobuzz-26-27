09 / Validation

Build the Android module, run JVM tests, then use focused Driver Station checks and tuning op modes.

The repo already separates compile-time validation, host-side unit tests, FTC SDK utility op modes, and Pedro tuning utilities. This chapter keeps those boundaries explicit so documentation does not blur a build step into a robot-on-field test.

What this chapter covers

Use this page before changing code in the matching source areas.

  • TeamCode/build.gradle declares JUnit 4, MockK, Android test support, and the TeamCode Android namespace.
  • UnitTestAll is the suite entry point for the JVM test tree under TeamCode/src/test/java.
  • tests/ftcSdk/androidTest is a reusable LinearOpMode base for profile-aware factory and hardware smoke tests.
  • tests/ contains focused Driver Station utilities such as drive, Limelight, and Pedro pathing checks.
  • pedroPathing/Tuning is the current tuning menu for localization, velocity, braking, and drive constants.
  • pid/autoTune/ contains relay-feedback tuning helpers that are calibration tools, not match entries.

What the JVM suite currently covers

UnitTestAll aggregates deterministic code that does not need a Control Hub.

  • Blackboard, timer, drive-vector, interpolation, and state behavior tests.
  • Control-loop tests for bang-bang, composite, and PIDF helpers.
  • MathUtilsTest and equation-math coverage for reusable calculations.
  • IntakeBallPathTest for camera-path generation logic.
  • FieldTest and RobotConfigurationTest for geometry and profile behavior.

What the FTC SDK utility layer does

The tests/ftcSdk package is for on-robot smoke checks that still respect profile configuration.

  • The shared androidTest base waits for start, updates both wrapped gamepads, runs one test body, then stops the op mode.
  • skipIfMechanismMissing(...) reports when a requested mechanism is not registered in Constants.currentBot.
  • Current factory checks include follower, robot drive, intake, vision, webcam, RGB indicator, motor, IMU, and slides tests.
  • These tests are intentionally narrow and should not be confused with full match validation.

What the Driver Station utility layer does

Other validation op modes under tests/ exercise higher-level behavior live on the robot.

  • PedroPathingTeleOpTest checks manual follower teleop control and on-demand path following.
  • Focused mecanum and intake utilities help validate direction, power, and field-centric behavior before using competition teleop.
  • Limelight and preseason utility op modes provide quick visibility into camera and follower integration during development.

Tuning boundary

Tuning.java recreates the follower through Constants.createFollower(hardwareMap) and exposes localization, automatic, manual, and simple path tests through a selectable menu. That makes it the right place for Pedro follower calibration, not the competition op modes.

Use pid/autoTune/ only when you are intentionally calibrating controller constants. Keep those relay-feedback tools separate from match lifecycle docs so readers do not mistake them for regular autonomous or teleop flows.

Fast validation order

Start with build and JVM feedback on the development machine, then move to FTC SDK factory checks, then move to the narrowest live Driver Station or tuning op mode that exercises the hardware path you changed.

This order keeps fast failures cheap and reserves robot time for checks that truly need hardware or driver-station interaction.

It also keeps tuning runs from masking compile or unit-test failures that could have been found earlier.
