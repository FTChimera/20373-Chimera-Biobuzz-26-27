09 / Validation

Prove each assumption at the right layer.

A successful Android build does not prove hardware wiring, and a successful hardware smoke test does not prove mathematical behavior. TeamCode separates host-side JUnit coverage, driver-station validation op modes, Pedro tuning flows, and relay-feedback PID tools so each question has an appropriate test surface.

Call the current profile follower in a safe runtime test

When verifying factory construction, begin with a no-motion setup like the existing follower factory test. This creates the follower through Constants, sets a declared pose, updates a few times, and reports measurements.

@Override protected void test(HardwareMap hardwareMap,
		GamepadEx gamepad1, GamepadEx gamepad2, Telemetry telemetry) {
	Follower follower = Constants.createFollower(hardwareMap);
	follower.setStartingPose(Constants.RED_DEFAULT_START_POSE);
	follower.update();
	follower.startTeleopDrive();
	follower.setTeleOpDrive(0, 0, 0, false);

	telemetry.addData("Pose", follower.getPose());
	telemetry.addData("Velocity", follower.getVelocity());
	telemetry.addLine("This test should not move the robot.");
	telemetry.update();
}

Know which test layer answers your question

LayerQuestion it answersLocation

Tuning op modeWhat measured values should feed follower/PID behavior?pedroPathing/Tuning.java or pid/autoTune/

Use JVM tests for code that does not need a robot

UnitTestAll.java is the explicit suite entry point. It currently includes Blackboard, DriveVector, Timer, PIDF, filters, input wrappers, interpolation, symbolic math, robot configuration, EquationCurve, and Field geometry coverage. Add a JUnit test when you change deterministic behavior; it is faster and safer than discovering a math error on the Driver Station.

./gradlew :TeamCode:testDebugUnitTest --console=plain
Recent geometry coveragelibrary/game/FieldTest.java checks contained, partial, and outside robot footprints as well as swept boundary crossings. That is the model for testing geometry without FTC hardware.

Use driver-station tests for construction and behavior

tests/ftcSdk/androidTest.java is a shared scripted LinearOpMode base for factory/device checks. Its profile-aware helpers let tests skip optional mechanisms with clear telemetry rather than crashing because a factory helper is unavailable in the selected profile.

Factory checks

FollowerFactoryTest, RobotDriveFactoryTest, IntakeFactoryTest, LimelightFactoryTest, RGBFactoryTest, and WebcamFactoryTest validate construction paths.

Direct-device checks

SlidesMotorTest and the device part of RGBIndicatorTest validate custom FTC hardware-device usage.

Drive checks

MecanumTeleOp provides raw direct drive/IMU inspection. MotorDirectionTest is a low-speed profile direction sanity check.

Integrated tests

TestPathPlanner, PlannerIntakeVisionAuto, and PreseasonWebcamAuto expose clearly scoped path/vision experiments.

Hardware safetyFactory success means construction succeeded, not that a mechanism is safe at full power. Keep wheels off the ground where practical, make moving tests single-purpose, and read test telemetry before assuming complete coverage.

Pedro tuning follows the profile follower

pedroPathing/Tuning.java exposes selectable Pedro tuner flows. It uses Constants.createFollower(hardwareMap), so it measures the profile currently selected by the codebase. Tune only after drivetrain names/directions, Pinpoint geometry, and basic localization are correct.

  1. Begin with safe drivetrain direction and localization checks.
  2. Use the relevant Pedro tuning flow for forward, lateral, turn, velocity, braking, PIDF, or path-shape behavior.
  3. Record measurements and move them into the appropriate robot profile field.
  4. Rebuild and rerun a behavior test after a configuration change.

PID AutoTune is a calibration-only exception

The three driver-station-visible pid/autoTune/ op modes wrap repo-local FTC adapters around the external relay-feedback algorithm. Their direct names, direction booleans, targets, and relay settings live in TuningConstants, rather than the normal profile-managed factory flow.

Op modeUse
PositionPIDTunerOpModePosition-control mechanisms.
VelocityPIDFTunerOpModeOne motor velocity behavior.
DualVelocityPIDFTunerOpModeMatched paired velocity systems such as flywheels.
Tuning safetyThese op modes intentionally move or spin hardware. Set safe limits and relay amplitude before Start, keep clear of mechanisms, and understand both automatic relay collection and the optional live test phase.

Finish with the build checklist

Normal TeamCode validation
./gradlew :TeamCode:assembleDebug --console=plain
./gradlew :TeamCode:lint --console=plain

Use the TeamCode debug build to catch source, Android, annotation-processor, and dependency wiring errors. Lint adds Android/static checks. Unit tests exercise pure logic. Then use the narrowest corresponding robot-side test for real hardware behavior.
