10 / Reusable Code

Keep shared code focused, tested, and robot-agnostic where possible.

The library/ package is where TeamCode keeps small reusable types and adapters: timers, drive vectors, control helpers, filters, interpolation, geometry, hardware wrappers, robot configuration, and planner building blocks. It should reduce duplication without becoming a place to hide match routines.

Call utility code from an OpMode loop

Shared helpers should make an OpMode smaller. This caller-side example tracks loop time, smooths a sensor value, and reports the result without putting a match routine into library/.

Timer loopTimer = new Timer(TimeUnit.MILLISECONDS);
LowPassFilter filteredDistance = new LowPassFilter(0.2);

waitForStart();
while (opModeIsActive()) {
    double rawDistance = distanceSensor.getDistance(DistanceUnit.INCH);
    filteredDistance.updateState(rawDistance);

    telemetry.addData("Raw inches", rawDistance);
    telemetry.addData("Filtered inches", filteredDistance.getState());
    telemetry.addData("Loop ms", loopTimer.dt());
    telemetry.update();
}

The library rule: utility or subsystem?

If the class mainly...Put it in...
Represents a value, performs reusable math, or adapts a low-level devicelibrary/
Owns a robot behavior, responds to driver bindings, and needs profile registrationmechanisms/
Coordinates a match or test flowAn op mode or planner layer

Examples of focused reusable types include Tuple, DriveVector, Timer, Direction, Motor, MathUtils, filters, interpolation helpers, and Field. A class that starts managing a physical mechanism should normally move to the Mechanism path.

Time, units, and small utilities

Timer is unit-aware and uses double time values for its getters, delta-time tracking, and threshold checks. Create it with a declared TimeUnit and keep that unit obvious at the call site. Use MathUtils for common unit conversion, heading normalization, FTC/Pedro pose conversion, and planner geometry helpers instead of creating local copies.

Timer retryTimer = new Timer(TimeUnit.SECONDS);
retryTimer.reset();
if (retryTimer.get() >= DETECTOR_RETRY_SECONDS) {
    // Choose the fail-safe route.
}
Loop helperOpModeHelper.kt is available for manual Lynx bulk caching and loop-dt tracking. It is lifecycle plumbing, not another input or scheduler abstraction.

Control and filtering utilities stay generic

PIDFController<T> and its related coefficient classes are generic helpers. They are appropriate when the controller should be reusable across state types; mechanism-specific telemetry, limits, and lifecycle still belong with the mechanism. NoiseFilter and LowPassFilter are lightweight signal conditioning tools.

// Conceptual low-pass rule used by the library:
filtered = filtered * (1 - alpha) + measurement * alpha;
  • A smaller alpha smooths more aggressively but reacts more slowly.
  • Call a controller/filter consistently each loop; inconsistent sample timing creates misleading tuning behavior.
  • There is no checked-in Kalman filter. Do not document or invoke one as a repo API.

Equation math and Pedro curve adaptation

The equation layer under library/math/ supports reusable symbolic/value expressions through Equation, Polynomial, Term, and internal SumEquation. Polynomial stores coefficients highest degree first. The Pedro-specific EquationCurve adapter belongs under pedroPathing/custom/ because it turns the general math surface into a followable Pedro custom curve.

Interpolation

LinearInterp provides table-like piecewise linear lookup; LagrangeInterp produces a reusable polynomial from samples.

EquationCurve

It checks that an equation matches requested endpoints within the repo's rough-equality contract and receives explicit heading interpolation.

Planner helpers

MathUtils supplies smoothing/tangent/spacing helpers used by dynamic vision path construction.

Field geometry

Field keeps JTS shape and robot-sweep computations reusable rather than embedding them in an autonomous command.

Math boundaryUse an equation curve when its function-through-endpoints model is clearer than Bezier control points. Do not use it merely because the math package exists; the ordinary Pedro line/curve path primitives remain the normal path-building tool.

Simulation is host-side support, not hardware validation

TeamCode/src/test/java/.../simulation/RobotSimulator.java and its related test surface provide a JVM-side place to exercise non-hardware behavior. Treat simulation results like any other host-side test: useful for logic and regression coverage, but not proof of motor direction, camera calibration, hub orientation, or field physics.

Workflow: extend shared code responsibly

  1. Find the narrowest existing type that already owns the concept.
  2. Keep the API small and name it for a reusable behavior, not a single match route.
  3. Add JVM tests when the behavior is deterministic and hardware-independent.
  4. Use the required external dependency only after inspecting the pinned Gradle artifact when the API is dependency-owned.
  5. Keep FTC lifecycle, profile registration, and match scheduling out of generic helpers unless the class is explicitly a wrapper/mechanism.
Before merging a library change
  • Can a second unrelated caller use this API?
  • Does it duplicate existing MathUtils, Timer, control, or wrapper behavior?
  • Does it have a focused unit test or a reason it cannot?
  • Would it be clearer as a Mechanism, path planner, or op-mode-local helper instead?
