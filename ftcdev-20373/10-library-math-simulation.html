10 / Reusable Code

Keep shared APIs small, Java-backed, and separated from match-specific lifecycle code.

library/ contains reusable control loops, filters, math, interpolation, hardware wrappers, planners, game types, and robot-profile helpers. Match orchestration belongs in op modes and planners; reusable calculations belong here only when more than one caller can share them.

What this chapter covers

Use this page before changing code in the matching source areas.

  • library/math/MathUtils.java is the current shared math hub; the guide should describe the Java file, not a deleted Kotlin equivalent.
  • MathUtils provides distance, heading, tangent smoothing, adaptive handle lengths, coordinate offsets, and unit conversion helpers.
  • IntakeBallPath relies on MathUtils for distance checks, heading deltas, waypoint smoothing, and robot-frame coordinate conversion.
  • library/control/, filters/, and interpolation/ host deterministic helpers that fit naturally in JVM tests.
  • library/game/ contains State, RobotMode, Field, and other reusable game-level types.
  • library/robot/ contains the current robot-profile and drivetrain helper types used by mechanisms and op modes.

MathUtils snapshot

These helpers show the kind of reusable geometry work already living in the shared math layer.

double distance = MathUtils.distance(x1, y1, x2, y2);
double heading = MathUtils.headingBetween(x1, y1, x2, y2);
Pose[] tangents = MathUtils.smoothTangents(waypoints);
double[] handles = MathUtils.adaptiveHandleLengths(waypoints, fraction);
Pose shifted = MathUtils.offsetPoseInRobotFrame(robotPose, forward, lateral, coordinateSystem);

What MathUtils currently exposes

The shared Java math file already spans several categories.

  • Angle and heading helpers such as headingBetween, headingDelta, and wrapAngle.
  • Vector normalization and waypoint-direction helpers used by curve generation.
  • Bezier support helpers such as smoothTangents, adaptiveHandleLengths, maxTurnAngle, and maxSpacingRatio.
  • Robot-frame offset conversion through the configured Pedro or FTC coordinate system.
  • Distance-unit and angle-unit conversion helpers through the nested MathUnits class.

Other reusable library boundaries

The rest of library/ supports the same idea of narrow, sharable responsibilities.

  • control/ contains controllers that are independent of any one mechanism lifecycle.
  • filters/ contains reusable low-pass and related helpers.
  • hardware/ contains direct wrappers for actuators, gamepads, webcams, and devices.
  • planners/ contains reusable autonomous modules and builder utilities rather than annotated op modes.
  • robot/ contains profile configuration, driver preference, and drivetrain support types.

Testing boundary for shared code

When a helper is deterministic and hardware-free, it should be validated in the JVM suite. MathUtilsTest, IntakeBallPathTest, FieldTest, and controller tests already follow that rule.

When a behavior needs hardware timing, motor power, or camera access, keep the reusable calculations in library/ but validate the integration path with Driver Station or FTC SDK utility op modes instead.

Extension rule for future shared APIs

Only promote logic into the library when it really is reusable.

  • Add a new shared helper only when two unrelated callers benefit from the same contract.
  • Keep match-specific sequencing in planners, op modes, or mechanisms instead of generic utility classes.
  • Prefer Java source that already matches the current package conventions used by the rest of TeamCode.
  • Add or update JVM tests when new reusable math or control behavior is introduced.

Shared code reminder

If a helper only exists to serve one mechanism’s private state machine, keep it near that mechanism. Promote it into library/ only after the source shows a real cross-package reuse case.
