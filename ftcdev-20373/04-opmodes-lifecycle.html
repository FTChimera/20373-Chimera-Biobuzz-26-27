04 / Execution

One OpMode owns the FTC lifecycle.

FTC code must choose a lifecycle shape before it chooses control logic. This repo uses both LinearOpMode and iterative OpMode; both are valid, but their initialization, active loop, and cleanup points are different.

Call a shared base by writing a small variant

For an alliance teleop, callers generally do not copy the entire control loop. They extend the repo base and supply only the selected start pose. The existing red wrapper follows this pattern.

@TeleOp(name = "My Red TeleOp", group = "0: TeleOp")
public class MyRedTeleOp extends TeleOp {
    public MyRedTeleOp() {
        super(AllianceColor.RED);
    }

    @Override protected Pose getStartingPose() {
        return Constants.RED_DEFAULT_START_POSE.copy();
    }
}

For pre-start preferences, select ConfigOpMode on the Driver Station, choose the D-pad item, then start it to persist Blackboard state. A match op mode reads that state; it does not reimplement the menu.

Choose the lifecycle that matches the control flow

UseWhen it fitsCurrent repository examples
LinearOpModeA clear sequential setup, waitForStart(), and active loop fits naturally.opModes/TeleOp.java, tests/PlannerIntakeVisionAuto.java, factory-test base flows
Iterative OpModeThe operation benefits from distinct init(), start(), loop(), and stop() hooks.opModes/IvyAuton.java, configs/ConfigOpMode.java
Lifecycle ruleNever use waitForStart() inside an iterative OpMode. Conversely, do not turn a LinearOpMode into an uncontrolled busy loop; use opModeIsActive() as the active condition.

The shared LinearOpMode teleop pattern

public void runOpMode() {
    GamepadEx driver = new GamepadEx(gamepad1);
    GpBindings bindings = driver.result();
    robot = Constants.createRobot(hardwareMap);
    drive = robot.require(RobotDrive.class);
    intake = robot.get(Intake.class);

    telemetry.addData("Status", "Initialized");
    telemetry.update();
    waitForStart();

    while (opModeIsActive()) {
        driver.update();
        robot.periodic(bindings);
        telemetry.addData("Pose", drive.getPose());
        telemetry.update();
    }
}

That sequence gives input edge detection a single update point, makes required/optional mechanism behavior explicit, and preserves telemetry ownership in the op mode.

The iterative autonomous pattern

IvyAuton resets the scheduler and builds shared resources in init(), schedules the sequence in start(), executes scheduler work and follower updates in loop(), then writes pose handoff and resets the scheduler in stop().

@Override public void init() {
    Scheduler.reset();
    follower = Constants.createFollower(hardwareMap);
    follower.setStartingPose(paths.getStartingPose());
    robot = Constants.createRobot(hardwareMap);
    intake = robot.require(Intake.class);
}
@Override public void loop() {
    Scheduler.execute();
    follower.update();
}
@Override public void stop() {
    Blackboard.put(Blackboard.Caption.POSE, follower.getPose().copy());
    Scheduler.reset();
}

Do not casually add another follower update loop around this base. The shared lifecycle already owns it.

Keep shared behavior in bases and selection in variants

Shared competition code belongs in a base class under opModes/. A Driver Station-visible variant under opModes/variants/ should be small: it supplies the alliance or path implementation and carries the FTC annotation. This reduces duplicate mechanism construction and keeps pose handoff consistent.

Existing patternTeleOp is a shared abstract LinearOpMode. Blue_TeleOp and Red_TeleOp are concrete wrappers that select an alliance-specific starting pose. IvyAuton is an abstract iterative base paired with an IvyAuton_Paths implementation.

Configuration and pose handoff use Blackboard

Blackboard stores typed runtime values for POSE, DRIVER, and ALLIANCE. It is not the robot configuration profile. ConfigOpMode is an iterative pre-start menu: init() builds selectable actions, init_loop() handles D-pad navigation, and loop() stops after the driver starts the op mode.

Before adding shared state
  • Add a typed Caption and a sensible default.
  • Decide which lifecycle owner writes it and which concrete mode consumes it.
  • Handle default state versus a meaningful restored value explicitly. Teleop pose wrappers currently guard the zero pose before reuse.
  • Use the config menu for preferences; do not multiply one-action annotated configuration op modes.
