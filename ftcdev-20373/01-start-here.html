01 / Foundation

Follow the aggregate robot flow that TeamCode/src actually uses.

The current code path is profile first: choose the active RobotConstants, create one aggregate Robot, build a matching State, start the robot once, then call periodic(State) until shutdown.

What this chapter covers

Use this page before changing code in the matching source areas.

  • Match code lives in tele/TeleOp.java and autos/Garden8.java, not in a removed opModes package.
  • mechanisms/ holds profile-managed behavior such as RobotDrive, Intake, Vision, and Robot.
  • library/ holds reusable helpers: math, planners, hardware wrappers, control loops, and profile definitions.
  • tests/ and tests/ftcSdk/ are Driver Station utilities, while src/test/java is the JVM unit-test tree.
  • State carries mode, alliance, bindings, helper access, and the current robot reference through the loop.
  • The active robot profile is Constants.currentBot = RobotConfigurations.FirstRobot() until source changes it.

Canonical lifecycle snapshot

This is the source-backed pattern to copy when you need a fresh control loop.

Robot robot = Constants.createRobot(hardwareMap, RobotMode.TELEOP);
State state = new State(RobotMode.TELEOP);
robot.start();
while (opModeIsActive()) {
    robot.periodic(state);
}
robot.stop();

Package map that matters now

These directories are the current architecture anchors described by the source tree.

  • autos/: competition autonomous entry points, with Garden8 as the current planner consumer.
  • tele/: competition teleop entry points, with TeleOp as the main annotated match program.
  • configs/: Blackboard state and the selectable configuration op mode.
  • pedroPathing/: tuning menu, alliance pose helper, and Pedro-specific adapters.
  • pid/autoTune/: relay-feedback calibration tools rather than match orchestration.
  • learning/: scratch or teaching code that should not drive current match documentation.

Startup facts to keep straight

The source makes a few lifecycle choices that the docs should mirror exactly.

  • Robot.start() starts OpModeHelper and immediately requests AprilTag vision when a Vision mechanism exists.
  • Robot.periodic(State) rejects a null or mismatched mode, refreshes helper timing and voltage, enriches State, then calls each mechanism.
  • Mechanism subclasses receive only HardwareMap and RobotConstants in their constructor contract.
  • Robot.stop() delegates to every mechanism stop(), closes the helper, and optionally persists end-of-match values.
  • TeleOp and Garden8 add their own entry-specific setup on top of the shared Robot lifecycle.

Current architecture boundary

Do not document stale sources from TeamCode/bin/ or any removed Ivy-specific op mode base classes as if they still drive the app. The live source tree under TeamCode/src is the only authority for this guide.

When a feature needs hardware ownership, place it in a mechanism or profile. When it needs deterministic math, geometry, filtering, or planning support, place it in library/ or pedroPathing/ instead of duplicating code in an op mode.

Safe documentation habits

Use these rules when expanding the rest of the guide.

  • Name the active classes directly: TeleOp, Garden8, Robot, PlanBuilder, Vision, and MathUtils.
  • Call out placeholder or unfinished areas such as Common pose values instead of presenting them as tuned field data.
  • Keep test boundaries explicit so readers know when a behavior belongs in JVM tests versus Driver Station validation.
  • Preserve navigation links between chapters so developers can move from architecture to validation without hunting for filenames.
