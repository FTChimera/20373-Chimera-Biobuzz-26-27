01 / Foundation

Start with the existing architecture.

TeamCode is not a collection of unrelated FTC examples. A program normally combines a robot profile, profile-managed mechanisms, an FTC lifecycle class, and optionally Pedro/Ivy behavior. Learn that route first; it keeps hardware naming, input updates, and telemetry coherent.

First call: a safe shared-architecture TeleOp

Start new driver-controlled work with this call pattern, not with a raw motor lookup. It is the smallest useful shape that uses profile creation, the input wrapper, aggregate updates, and telemetry.

@TeleOp(name = "My First TeamCode TeleOp")
public class MyFirstTeleOp extends LinearOpMode {
	@Override public void runOpMode() {
		GamepadEx driver = new GamepadEx(gamepad1);
		GpBindings bindings = driver.result();
		Mechanisms mechanisms = Constants.createMechanisms(hardwareMap);
		RobotDrive drive = mechanisms.require(RobotDrive.class);

		waitForStart();
		while (opModeIsActive()) {
			driver.update();
			mechanisms.periodic(bindings);
			telemetry.addData("Pose", drive.getPose());
			telemetry.update();
		}
	}
}

Map the packages before editing

Robot behavior

mechanisms/ owns profile-managed subsystems such as RobotDrive and Intake. opModes/ coordinates them for match use.

Reusable code

library/ contains utilities, input wrappers, math, robot profiles, hardware wrappers, field geometry, and planner components. It should not become a second match-strategy layer.

Validation code

tests/ contains driver-station-visible checks; src/test/java/ contains host-side JUnit tests. Use a test for an uncertain hardware or algorithm assumption before shipping match logic.

Pedro-specific code

pedroPathing/ contains Ivy adapters, tuning selection, and Pedro custom adapters. Path planner utilities live at library/planners/.

Read firstConstants.java, library/robot/RobotConfigurations.java, mechanisms/Mechanism.java, mechanisms/Mechanisms.java, and one target op mode. Those five surfaces tell you how a feature is created and driven.

The standard implementation workflow

  1. Identify whether the change is a mechanism, reusable utility, profile configuration, pathing behavior, or test.
  2. Read the closest existing class and its current caller. Prefer the nearest existing pattern over a generic FTC tutorial.
  3. For a profile-managed subsystem, implement the mechanism, register it in each appropriate profile, and expose a narrow factory only if callers need one.
  4. Use one FTC op mode lifecycle owner. Initialize hardware before waitForStart() in a LinearOpMode, or in init() for iterative OpMode.
  5. Add focused validation: a host test for pure logic, a driver-station test for construction/hardware, then the TeamCode build.
// Shared TeleOp uses the aggregate pattern.
Mechanisms mechanisms = Constants.createMechanisms(hardwareMap);
RobotDrive drive = mechanisms.require(RobotDrive.class);
Intake intake = mechanisms.get(Intake.class); // Optional across profiles

Respect the important boundaries

Profile-managed mechanism versus direct FTC device

A class extending Mechanism participates in profile registration and reflection-based construction. A custom direct FTC device under library/hardware/hardwareDevice/, such as SlidesMotor, is fetched through hardwareMap.get(...) in an SDK-level flow. These are deliberately different paths.

Match code versus test code

Some tests intentionally use direct SDK APIs. That does not make raw construction the TeamCode match standard. Keep proof-of-concept code explicit and do not copy it into shared teleop/autonomous code without first moving the behavior into a wrapper or mechanism.

Configuration versus state

RobotConfigurations describes a robot. Blackboard stores runtime state shared between op modes, currently pose, driver preference, and alliance. Do not put a selected runtime driver preference into a static profile.

Build your first program safely

Minimum path to a runnable program
  • Start with an existing tests/ftcSdk/ factory check when verifying hardware construction.
  • Use ConfigOpMode before a match when you need to set Blackboard pose, driver, or alliance preferences.
  • Use a concrete annotated wrapper for Driver Station visibility; leave reusable code unannotated and abstract.
  • Show initialized status and relevant mechanism/pose telemetry.
  • Run the TeamCode debug build before connecting to hardware.
