05 / TeleOp

Update input once, then let RobotDrive own driving.

The TeamCode input path is GamepadEx → GpBindings → Mechanism.periodic(...). Drive values become a DriveVector, and RobotDrive delegates motor/follower behavior to MecanumDrive. That separation prevents duplicated deadzones, sign flips, and field-centric math.

Call the normal teleop input path

This loop is the preferred call-site example. It updates one wrapper, forwards its result to every registered mechanism, and lets RobotDrive read its configured sticks and heading-reset button.

GamepadEx driver = new GamepadEx(gamepad1);
GpBindings bindings = driver.result();
Robot robot = Constants.createRobot(hardwareMap);
RobotDrive drive = robot.require(RobotDrive.class);

waitForStart();
while (opModeIsActive()) {
    driver.update();
    robot.periodic(bindings);
    telemetry.addData("Pose", drive.getPose());
    telemetry.update();
}

GamepadEx is stateful: update first

GamepadEx wraps FTC gamepad state with buttons, sticks, triggers, touchpad information, rumble, and LED support. Its readers implement edges and toggles, so the wrapper must receive exactly one update() each control loop before values are read.

GamepadEx driver = new GamepadEx(gamepad1);
GpBindings bindings = driver.result();

while (opModeIsActive()) {
    driver.update();
    if (driver.wasJustPressed(Button.A)) {
        // Edge behavior is valid only after update().
    }
    robot.periodic(bindings);
}
Do not double-shape inputGamepadEx can apply a stick curve, while the normal drive path also has a MecanumDrive curve. Shared teleop keeps the wrapper near-neutral and applies its chosen curve through RobotDrive.setStickCurve(...). Do not apply both unless that is explicitly the intended behavior.

GpBindings makes mechanisms input-agnostic

GpBindings exposes the current wrapper readers to a mechanism. RobotDrive.ROBOT_DRIVE_PARAMS stores the translation stick, rotation stick, and zero-heading button. Intake.INTAKE_PARAMS stores forward/reverse command descriptors. The mechanism resolves those descriptors on every periodic call instead of reaching directly for gamepad1.

// RobotDrive turns its configured reader choices into one DriveVector.
Stick translation = bindings.getCommand(params.TRANSLATION_STICK);
Stick rotation = bindings.getCommand(params.ROTATION_STICK);
return new DriveVector(
    translation == null ? 0 : translation.getY(),
    translation == null ? 0 : translation.getX(),
    rotation == null ? 0 : rotation.getX()
);
  • Add a reusable control mapping to the owning mechanism parameters.
  • Use GpBindings.getCommand(...) rather than a raw gamepad cast.
  • Keep one aggregate robot.periodic(bindings) call in shared teleop.

Follow the drive pipeline

  1. RobotDrive.periodic(...) calls MecanumDrive.periodic(), which records the pre-update pose and updates the follower.
  2. It reads configured sticks and produces a DriveVector.
  3. It honors the configured zero-heading button and delegates to setTeleOpDrive(...).
  4. MecanumDrive copies the vector, applies the selected stick curve, and chooses manual motor output or Pedro follower teleop based on the profile.
// Do not copy this math into an op mode; use the mechanism surface.
drive.setStickCurve(x -> Math.signum(x) * x * x);
drive.startTeleOpDrive();
// Later: aggregate periodic input updates drive behavior.

Field-centric behavior is a preference, not another teleop mode

The selected Blackboard.Caption.DRIVER value controls Driver.USE_FIELD_CENTRIC. MecanumDrive uses that preference when a caller uses the normal setTeleOpDrive(vector) surface. For manual drive, the shaped vector applies a forward inversion and uses DriveVector.rotateFieldCentric() with the pose heading minus the heading offset. For follower drive, Pedro receives the shaped values and field-centric flag.

Heading resetRobotDrive maps its zero-heading action through ROBOT_DRIVE_PARAMS.ZERO_HEADING_BUTTON, defaulting to Button.BACK. It records the current follower heading as the offset; it is not the same as changing the global pose heading.

Validate controls without guessing

Driver-control checklist
  • Confirm raw stick orientation and curve once, then retain one shaping owner.
  • Run tests/MecanumTeleOp.java for direct drivetrain/IMU checks.
  • Run tests/MotorDirectionTest.java at low power when validating profile directions and optional intake direction.
  • Verify field-centric direction after an explicit heading reset.
  • Confirm the selected Blackboard driver preference is what you expect before attributing a behavior change to drive math.
