05 / TeleOp

Update both controllers once per loop and let RobotDrive own drive dispatch.

DualGamepad is the competition input wrapper. It exposes two GamepadEx objects, updates both together, and returns a GpBindings view that match code passes into State. Drive math and follower/manual switching stay inside RobotDrive and MecanumDrive.

What this chapter covers

Use this page before changing code in the matching source areas.

  • DualGamepad.update() must run before reading edge-triggered buttons, sticks, triggers, or touchpad state.
  • DualGamepad.result() creates the binding view consumed by TeleOp and other driver-facing loops.
  • RobotDrive.periodic(State) reads the configured translation and rotation sticks from bindings during teleop.
  • MecanumDrive.setTeleOpDrive(DriveVector) chooses field-centric mode from the Blackboard driver preference when the overload without an explicit boolean is used.
  • Driver.DEFAULT, ATHARVA, SHLOK, and EASON currently enable field-centric drive; SIMPLE disables it.
  • ConfigOpMode is where driver preference is selected at runtime.

Competition input snapshot

This pattern matches the current teleop entry and keeps controller state synchronized.

DualGamepad drivers = new DualGamepad(gamepad1, gamepad2);
State state = new State(RobotMode.TELEOP);
state.setGpBindings(drivers.result());
while (opModeIsActive()) {
    drivers.update();
    robot.periodic(state);
}

DualGamepad surface area

The wrapper is broader than just two stick getters.

  • There are constructors for raw FTC gamepads, custom deadzone and curve settings, or two already-built GamepadEx instances.
  • The class forwards button, toggle, trigger, stick, touchpad, LED, and rumble helpers to both controllers.
  • updateCommand() returns an Ivy command that continuously refreshes both wrapped controllers.
  • setStickCurve(...), setJoystickDeadzone(...), and setTriggerThreshold(...) apply shared settings to both pads.

RobotDrive responsibilities

The teleop drive mechanism owns more than raw power calculation.

  • It starts manual teleop drive through the follower and, when enabled, through the manual drivetrain path too.
  • It tracks follower mode as MANUAL, FOLLOWING, HOLDING, or TURNING.
  • It zeroes heading when the configured zero-heading button is pressed.
  • It returns to manual mode after follower actions finish unless hold-end behavior keeps the robot holding position.
  • Its teleop periodic path does not duplicate path-following math in the op mode.

MecanumDrive responsibilities

Field-centric and stick shaping live one layer lower in the drivetrain implementation.

  • Manual vectors are copied, stick-curved, and optionally rotated field-centrically using the robot heading minus the heading offset.
  • Follower-drive teleop vectors are also stick-shaped before being passed to Pedro follower teleop control.
  • The no-boolean setTeleOpDrive overload reads Blackboard.Caption.DRIVER and uses the chosen driver preference.
  • zeroHeadingOffset() snapshots the current follower heading so later field-centric calculations use that as zero.

Validation boundary

When you need to check motor directions, field-centric response, or manual driving, use the focused Driver Station programs under tests/ rather than changing match teleop first. Current examples include drivetrain-specific teleops and Pedro pathing tests.

Keep new driver-facing math in the drive stack, not in a second copy of joystick math inside an op mode. That keeps competition behavior and validation behavior aligned.

Blackboard driver preference

The active driver profile is intentionally lightweight: it only carries the field-centric preference that MecanumDrive reads when no explicit boolean override is supplied.
