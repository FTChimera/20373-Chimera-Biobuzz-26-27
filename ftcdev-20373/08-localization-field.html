08 / Position

Keep follower localization, vision relocalization, and field geometry roles explicit.

The active profile builds the follower, the drive mechanism owns the working pose, Vision caches and optionally blends Limelight MT2 updates, and Field supplies geometric contact helpers rather than a match planner.

What this chapter covers

Use this page before changing code in the matching source areas.

  • Constants.createFollower(hardwareMap) delegates follower construction to the active RobotConstants profile.
  • RobotDrive and MecanumDrive own the live pose used by teleop, path following, and autonomous park motion.
  • Vision.forceRelocalize(RobotDrive) is the explicit path that applies a valid camera pose to the drive localizer.
  • Vision.periodic(State) updates robot orientation and Limelight results but does not automatically overwrite pose every cycle.
  • Field uses JTS geometry to create polygons, circles, robot footprints, sweeps, and contact-state checks.
  • pedroPathing/custom/LimelightPinpointLocalizer exists in source, but follower creation still comes from the active robot profile factory.

Explicit relocalization snapshot

This abbreviated flow shows why docs should describe vision pose updates as intentional, not automatic.

if (!isRunning()) return false;
if (!hasValidResult()) return false;
setPipeline(Pipeline.APRIL_TAG);
updateRobotOrientation(drive.getPose().getHeading());
update();
Pose visionPose = getCachedPose();
drive.setPose(visionPose.linearCombination(drive.getPose(), 0.3, 0.7));
setPipeline(pipeline);

Follower and pose ownership

The current architecture keeps pose authority inside the drive stack.

  • Robot.setStartingPose(...) forwards to requireDrive().setStartingPose(...).
  • Robot.getPose(), setPose(...), and velocity accessors all forward to the drive mechanism.
  • Robot.getPoseCompensatedForVelocity() estimates an end pose by adding velocity to the current follower pose before persistence.
  • Robot.moveToPark() builds a linear Pedro path from the current drive pose to the selected park pose.

Vision facts worth keeping in docs

The Limelight wrapper does several useful things without becoming the sole pose owner.

  • Pipelines are wrapped as APRIL_TAG, COLOR, and NEURAL_DETECTOR.
  • start(pipeline), setPipeline(...), getFiducials(), getColors(), and getDetectors() expose the main result surfaces.
  • Relocalization temporarily forces the AprilTag pipeline, updates camera orientation from the current drive heading, and blends vision with odometry at a fixed confidence weight.
  • getCachedPose() returns the latest MT2 pose estimate, but calling it alone does not change the robot pose.

Field helper boundary

Current source uses Field as a geometry utility rather than a full strategic model.

  • It can create ordered polygons and circles from Pedro poses.
  • It computes robot footprints and swept volumes from pose, velocity, and delta time.
  • It classifies contact as CONTAINED, PARTIAL, or OUTSIDE.
  • It is useful for spatial checks and tests, but it is not the current route generator for match autonomous.

Localization validation boundary

Use pedroPathing/Tuning for localization and follower calibration, and use narrow Driver Station tests when you need to verify a specific sensor or relocalization path on hardware.

Keep coordinate-system conversions centralized through MathUtils and the configured FTC coordinate system so planner, Limelight, and Pedro code agree on axes and headings.

Explicit over implicit

This codebase favors deliberate pose changes. If documentation describes a camera pose update, it should also name the call site that chooses to apply it.
