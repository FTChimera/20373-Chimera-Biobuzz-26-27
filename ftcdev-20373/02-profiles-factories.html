02 / Configuration

Profiles decide what the robot can construct.

The configuration stack is intentionally layered. Constants is the op-mode-facing convenience surface; RobotConfigurations declares named robot presets; RobotConstants holds the builder data and constructs a follower or a registered mechanism.

Call factories from an OpMode

Most op modes should call the profile-facing helpers, then use typed aggregate lookups. This is the usual caller-side code; profile builders stay out of the op mode.

@Override public void runOpMode() {
    Robot robot = Constants.createRobot(hardwareMap);
    RobotDrive drive = robot.require(RobotDrive.class);
    Intake intake = robot.get(Intake.class);
    IMU imu = Constants.createIMU(hardwareMap);

    telemetry.addData("Configured", robot.getConfiguredMechanismClasses());
    telemetry.addData("Has intake", intake != null);
    telemetry.update();
    waitForStart();
}

// Constants is a delegation boundary, not a second configuration store.
public static RobotDrive createDrive(HardwareMap hardwareMap) {
    assertHasMechanism(RobotDrive.class);
    return currentBot.createMechanism(hardwareMap, RobotDrive.class);
}

Registration is a runtime contract

A factory helper existing in Constants does not mean every profile supports its mechanism. The selected profile must register the class. configureDriveMechanisms() supplies the standard RobotDrive registration; optional features require their own .addMechanism(...) call.

return new RobotConstants()
    .configureDriveMechanisms()
    .addMechanism(Intake.class, new Intake.INTAKE_PARAMS()
        .hardwareMapName("intake")
        .intakeMotorDirection(Direction.REVERSE))
    .addMechanism(Limelight.class, new Limelight.LIMELIGHT_PARAMS()
        .hardwareMapName("limelight"));
Source of truthInspect RobotConfigurations.java before assuming that an optional mechanism is available. Use Constants.hasMechanism(SomeMechanism.class) in cross-profile test code.

Choose the correct factory

Aggregate mechanism set

Constants.createRobot(hardwareMap) constructs every class registered on the active profile. Shared teleops use require(RobotDrive.class) and nullable get(...) calls.

One profile mechanism

Constants.createIntake(...), createLimelight(...), or createDrive(...) assert registration first, then use RobotConstants.createMechanism(...).

Follower and IMU

createFollower(...) and createIMU(...) are profile-configured helpers, not mechanism factories. The IMU helper initializes REV Hub orientation but does not reset yaw.

Direct custom device

Use hardwareMap.get(SlidesMotor.class, ...) only for a custom SDK device/test flow, not for a profile-managed subsystem.

Failure modeassertHasMechanism() throws before a wrapper can quietly disable itself. This is useful: it tells you that profile registration, not a motor name, is the first bug to fix.

Local parameter overrides belong with the mechanism

Mechanisms define nested builder-style parameter classes implementing Mechanism.Params. The base Mechanism.resolveParams(...) asks the active profile for an override, copies it, and invokes updateFromBot(bot). This lets the same mechanism retain its own meaningful defaults while a robot profile can override hardware-dependent values.

params = resolveParams(Intake.class, new Intake.INTAKE_PARAMS());
if (!params.ISBEINGUSED) return;
Intake_Motor = new Motor(map, params.HARDWAREMAP_NAME);
Intake_Motor.setDirection(params.INTAKE_MOTOR_DIRECTION);
  • Keep drive, localizer, and IMU settings in RobotConstants.
  • Keep a mechanism's power presets, bindings, and local hardware fields in its nested params type.
  • Adding parameter overrides does not register a class. Registration and parameter data are separate.

Workflow: change or add a robot profile

  1. Copy the closest preset in RobotConfigurations; retain its builder order so drive, IMU, Pinpoint, follower, registration, and compatibility fields stay readable.
  2. Update all four drive names and directions together.
  3. Set IMU name and logo/USB orientation together; then validate it with Constants.createIMU(...).
  4. Keep Pinpoint offsets, encoder directions, unit, and resolution together in PinpointConstants.
  5. Register each supported profile mechanism explicitly and provide its params override when needed.
  6. Use the factory tests and a safe drivetrain test before calling the profile match-ready.
