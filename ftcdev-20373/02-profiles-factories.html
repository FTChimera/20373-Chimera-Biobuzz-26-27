02 / Configuration

Profiles decide which mechanisms, followers, and names the aggregate robot can build.

Constants is the factory surface, RobotConfigurations declares preset robots, and RobotConstants stores the data used to create the follower and every registered mechanism.

What this chapter covers

Use this page before changing code in the matching source areas.

  • Constants.currentBot is compiled to RobotConfigurations.FirstRobot() right now.
  • The profile owns motor names, directions, IMU orientation, Pinpoint setup, follower constants, and registered mechanism params.
  • Constants.createRobot(...), createFollower(...), and createMechanism(...) all route through the active profile.
  • Constants.hasMechanism(...) and assertHasMechanism(...) gate cross-profile code paths and tests.
  • FirstRobot() still contains zeroed velocity, heading-PID, and centripetal values that must be treated as placeholders.
  • Profile selection is a source edit and rebuild, not a runtime menu choice.

Factory snapshot

These methods show the intended entry points for match code and validation code.

public static final RobotConstants currentBot = RobotConfigurations.FirstRobot();
public static Robot createRobot(HardwareMap hardwareMap, RobotMode robotMode) {
    return new Robot(hardwareMap, currentBot, robotMode);
}
public static boolean hasMechanism(Class mechClass) {
    return currentBot.Mechanisms.contains(mechClass);
}

What FirstRobot currently configures

The active profile in RobotConfigurations.java hard-codes these major categories.

  • Drive motor hardware map names are frontLeft, frontRight, backLeft, and backRight.
  • Motor directions are reverse on the left side and forward on the right side.
  • The IMU uses hardware map name imu with logo facing up and USB facing forward.
  • Pinpoint uses hardware map name pinpoint with measured pod offsets and reversed encoder directions.
  • Registered profile-managed mechanisms are the drive stack, Intake, and Vision.
  • Follower-drive compatibility is enabled with useFollowerDrive(true).

How params are propagated

Mechanism-specific tuning is copied rather than shared by reference.

  • Mechanism.resolveParams(...) pulls the active override from RobotConstants and calls updateFromBot(bot).
  • Each mechanism param type implements copy() so per-profile overrides do not mutate shared defaults.
  • Profile code is where you register a mechanism and attach its params in one place.
  • Direct SDK device wrappers under library/hardware/hardwareDevice are not added through the aggregate robot factory.

Practical profile cautions

Because currentBot is a static final assignment, a stale APK can still point at an older profile after source changes. Rebuild and redeploy after editing names, directions, or follower constants.

The current FirstRobot() profile compiles, but its xVelocity, yVelocity, heading PIDF values, and centripetal scaling are still placeholder zeros. Document them as incomplete, not match-ready.

When to use which factory

Match code and tests do not need the same entry point every time.

  • Use createRobot(hardwareMap, mode) when multiple mechanisms must share one lifecycle and one State.
  • Use createFollower(hardwareMap) for Pedro tuning or focused follower validation under pedroPathing/Tuning and test op modes.
  • Use createMechanism(...) or require(...) in narrowly scoped tests that only need one profile-managed mechanism.
  • Use hasMechanism(...) before running cross-profile FTC SDK tests that may be absent on another robot profile.
